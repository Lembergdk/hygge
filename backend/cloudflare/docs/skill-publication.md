# Shared website skills V2 foundation

Wave 1 code only. No endpoints, bindings, policy registry entries, migrations or publication paths are activated. Existing V1 browsing/skills, routing, models and user state are unchanged. This foundation implements shared schema/privacy policy and real D1 SQL transactions; trusted broker transport, crypto adapters and current call-site integration remain Wave 2/root work.

## Components

- `skill-contract.ts`: strict shared body vocabulary, private evidence source and trusted publication interfaces. No owner identity or private evidence is included in a public body or publication claim.
- `skill-policy.ts`: exact keys, type/UTF-8 size limits, Unicode validation, known site/route/control/field/pitfall IDs, parameter references and domain-separated SHA-256 canonical hashing. Hashing is the RFC 8785-compatible restricted subset used here (nonnegative safe integers/JSON strings/bools/null, recursively sorted objects); it deliberately rejects other numeric values. Caller-supplied free prose, raw URLs, selector text, scripts and values are not shared.
- `PrivateSkillValidator`: inside the trusted owner DO, loads the original private candidate/context, fetches canonical completion receipts, requires three distinct successful run IDs with the same candidate hash/site/outcome/owner and valid postcondition evidence, and checks each receipt's committed artifact coverage. No caller-provided corroboration count is accepted. Committed historical receipts remain valid after runtime replacement; new signing authority must be current. C's `getCanonicalRunReceipt` and `verifyDurabilityCoverage` methods are the adapter boundary.
- `SharedSkillPublisher`: requires a trusted service authorizer and real cryptographic attestation verifier; absence fails closed. Attestations bind environment, audience, policy version, exact capsule hash, server-created idempotency key, token ID, expiry and distinct success count. This module never puts a signing credential into model/VM execution. The issuer and verifier are intentionally injected; test signers are not a production transport.
- `D1SkillPublicationRepository`: prepared parameterized SQL, atomic D1 `batch()` transactions, content deduplication, serialized version allocation, idempotent usage maintenance, irreversible-through-success quarantine and transactional admission/consumption. Adds V2 tables only through migration `0008_shared_skills_v2.sql`.

## Trusted boundary requirements

`OwnerEvidenceSource` is an application-owned adapter, not a JSON body or model tool implementation. `authorizeOwner` authenticates user/workspace/environment and current operation capability. Loading a candidate returns the immutable original candidate hash, original and corroborating private context, and required private artifact refs. The canonical ledger, not this module, establishes that confirming runs actually pinned the hash and authoring binds its final derived hash exactly once. Durability validation must cover original context, postcondition evidence and all declared completion dependencies via A/C verified manifest receipts. A local fsync or uploaded-but-unverified object is insufficient. Raw evidence and private reference hashes never enter public skill rows.

`AttestationIssuer` runs only after those checks in the trusted owner backend. The signing broker must recheck live lineage on issuance (including revocation during asynchronous validation), authenticate issuer/audience, enforce short expiry, and use its protected key. `AttestationVerifier` must verify signatures and trusted issuer/policy, not decode a client assertion. Root's crypto helper will be wired to these interfaces; production connection is not established here. `ServiceAuthorization.authorize(token, operation, binding)` must authenticate an authorized trusted backend and bind that exact operation payload. Ordinary user/runtime scopes cannot grant arbitrary usage results, quarantine privilege, or admission consumption. Usage tokens must derive from canonical execution receipts, including success and skill implication evidence. No arbitrary user boolean may become population reliability data. HTTP adapters must map thrown policy conflicts to stable code-only failures and never expose SQL errors/body content.

No default site registry is installed. `createReviewedRegistry` consumes trusted, independently reviewed application configuration and clones it defensively. Syntactic checks alone cannot establish a route contains no personal identifier: trusted registry ingestion must verify generic public evidence or documented backend review before calling the factory. Marking an entry `independent_public_evidence` is provenance supplied by trusted application code, not proof fetched by this module. Runtime/request registry additions are forbidden. An authenticated-only or ambiguous control remains private until reviewed. Registry evidence retrieval/SSRF validation and review tooling are future integration work.

## Quarantine and concurrency

Publication/usage/maintenance batches serialize at D1's write authority. One-use admission IDs bind exact skill/version/epoch; consumption binds one opaque private effect/generation digest supplied by the owner DO. No personal effect body is stored in the shared DB. Retrying consumption for the same effect is idempotent; the owner effect ledger must ensure a repeated receipt response does not resend an external action. A changed binding is denied.

Consumption is the final authority admission point, atomically checking current status/epoch/expiry. Quarantine prevents consumption/admissions ordered afterward, including warm-cache use. An action consumed before quarantine may already be dispatched and cannot be retroactively undone; ambiguous effects reconcile through C's ledger. Registry outage fails shared skill use closed and allows root to start a fresh private no-skill decision. Do not treat stale cached guidance as authorized.

D1 read replicas require a primary-consistent session for resolution/status reads at activation (e.g. `env.DB.withSession('first-primary')` supplied to the repository). Write-side admission always checks authoritative status in a transaction. `batch()` rollback guarantees come from the [official D1 API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch); offline tests execute the identical SQL against real SQLite with atomic BEGIN/COMMIT/ROLLBACK, not a map that imitates query results. Those tests do not prove deployed D1 routing, latency or provider acceptance.

Migration preserves V1 tables and history; it does not validate old free prose or make it safe by wrapping V2 metadata. Existing skills must be separately converted and privacy-validated before a future reader switch. Safe generic outcomes/version lookup/confidence failure demotion remain compatible. Get BOB lifecycle components may be reused, but team/BOB-global source sharing is not imported into this cross-user privacy boundary.

Read/use validation is repeated under the current policy and reviewed registry. Resolution, new admission, and admission consumption reject a stored skill if its policy version is incompatible, content hash mismatches, metadata disagrees with the body, or any formerly valid route/control/field-set reference is no longer reviewed. Admission/consumption SQL also conditionally matches the validated body, hash, policy, epoch and applicable version, closing the stored-body mutation race between validation and authoritative use. A previously issued admission is insufficient after policy/registry removal. Registry configuration is an immutable reviewed snapshot per publisher instance; switching policy deployments must drain old service instances rather than assume a new registry object changes existing instances.

## Checks

Run `node --experimental-strip-types --test test/skill-policy.mts test/skill-publication.mts` and `./node_modules/.bin/tsc --noEmit`. Tests use Node 22's experimental `node:sqlite`; application code has no dependency on that module. The test issuer/verifier is an explicitly fake trusted transport, used to isolate the real policy and SQL behavior. Before activation, test production broker signatures, C/A ledger/manifest adapters, actual reviewed site registry, trusted usage tokens and owner-effect binding, primary-session routing, and real two-user behavior in staging.
